# LinQOrbit — Frontend

Next.js 16 (App Router) + TypeScript + Tailwind CSS v4. Recrutement platform : candidats, recruteurs, entreprises, offres, candidatures, matching.

## Stack

- **Next.js 16** App Router, `app/` à la racine (pas de `src/`), Turbopack
- **TypeScript** strict, alias `@/*` → racine du projet
- **Tailwind CSS v4** (`@import "tailwindcss"` dans `app/globals.css`, config via `@theme`)
- **Zustand** — état client global uniquement
- **TanStack Query** — état serveur (fetching, cache, mutations)
- **Axios** — instance dans `lib/api/axios.ts`
- **React Hook Form + Zod** (`@hookform/resolvers`) — formulaires et validation

Interdits : Redux ou autre state manager global, shadcn/ui et toute bibliothèque externe de composants UI (le design system maison de `components/ui/` fait foi), styling autre que Tailwind.

## Architecture feature-oriented

```text
app/          routing et layouts Next.js UNIQUEMENT — route groups (public), (auth), (dashboard)
components/   composants réellement partagés entre domaines (layout/, navigation/, ui/)
features/     logique par domaine : auth, admin, candidate, recruiter, company, job-offer, application, matching
lib/          infrastructure : api/ (axios), validations/ (schémas Zod transverses), utils/
hooks/        hooks génériques uniquement
stores/       Zustand — état client global uniquement
types/        types d'entités de données partagées (shapes API + session : auth.ts, candidate.ts)
config/       configuration
```

Règles :
- Une feature regroupe ses propres composants, pages, données et logique métier quand elle en a besoin : `features/job-offer/…`. Les hooks vont dans `hooks/`, les schémas Zod dans `lib/validations/`, les modules API dans `lib/api/` (voir « Placement des fichiers »). Ne rien mettre dans `components/` qui n'est pas réellement partagé.
- **Imports entre features** : une feature consomme d'abord les modules `*-shared` d'une autre (helpers, constantes, petits composants). Un **fragment de vue** d'une autre feature n'est importé que lorsque la réutilisation est une décision produit, jamais par commodité ; il reste alors dans sa feature d'origine (le déplacer sous `components/` le rendrait faussement générique). Arêtes assumées (TD-048) : `features/admin/user-detail-view.tsx` → `ProfileSections` de `features/candidate/profile-view.tsx` (profil en lecture identique à la vue candidat, D38) ; `features/recruiter/recruiter-workspace.tsx` → `JobOffersSection` de `features/job-offer/job-offers-section.tsx` (le workspace compose la section offres) ; `features/application/offer-banner.tsx` → `PublicJobArticle` (accordéon = détail de l'offre identique à la fiche publique, D59) et `MetaChip`/`OFFER_SALARY_CHIP` de `features/job-offer/job-offer-card.tsx` (même langage de chips que la fiche) ; `features/application/apply-view.tsx` → `MatchingPanel` de `features/matching/matching-panel.tsx` et `AssessmentReview` de `features/matching/assessment-review.tsx` (le parcours compose le matching et la contestation, D58, D62–D59) ; `features/application/assessment-focus.tsx` → `ClarificationPanel` de `features/matching/clarification-panel.tsx` (l'évaluation ouverte est le contenu central du parcours, D69). Toute nouvelle arête de ce type s'ajoute ici ; jamais d'import circulaire entre features.
- Ne pas créer de dossiers/sous-dossiers vides « pour la forme ». Créer un sous-dossier seulement quand du code le justifie.
- Pas de couches `services/`, `managers/`, `providers/` ni d'abstractions (factories, repositories) sans besoin réel.
- `app/` ne contient pas la logique métier : les pages appellent les composants et hooks des features.

Un fichier créé hors de son dossier d'architecture est une erreur, même s'il compile.
Avant de créer un fichier, vérifier ce tableau — **en cas de doute, demander plutôt que de créer au mauvais endroit** :

## Séparation des responsabilités (state)

```text
TanStack Query   état serveur : données API, cache, fetch, mutations, sync backend
Zustand          état client : UI, préférences, état global vraiment nécessaire
React Hook Form  état de formulaire
Zod              validation / schémas
```

Ne jamais mettre de données serveur dans Zustand « parce que Zustand est dispo ».

- **Clés TanStack Query** : toujours via `hooks/query-keys.ts` (`queryKeys.<domain>.…`) — aucun littéral `queryKey: [...]` hors de ce registre, ni clé exportée depuis un hook ; invalider une famille = sa clé racine (ex. `queryKeys.candidate.reference` pour les 4 listes de référence, `queryKeys.jobOffers.list` + `queryKeys.jobOffers.detail(id)` après une mutation d'offre).

## Formulaires (React Hook Form + Zod)

- **Jamais de `z.preprocess` ni de `transform` dans un schéma branché à `zodResolver`** : dès que `z.input ≠ z.output`, `zodResolver(schema)` n'est plus assignable à `useForm<Values>()` (erreur TS). Les champs facultatifs sont donc **toujours du `string`** : `""` = vide, et la couche API (`lib/api/*.api.ts`) convertit `""` → `null` (et une saisie numérique en `string` → `number | null` avant l'envoi).
- Ce que la conversion API fait pour le profil candidat : dates/pays/bio/issuer/role/technologies/description `""` → `null`, `yearsExperience` `"7"` → `7`, `issuer`/`issuedAt` conservés seulement si `linkType === "certification"`.
- Réflexe : une règle métier qui dépend d'un **autre champ** (fin de carrière postérieure au début, doublon dans la liste) vit dans un `.superRefine` du schéma ; une règle qui **masque un champ** ne peut pas y vivre (l'erreur serait inatteignable) → on vide/masque dans la couche API.
- Listes d'objets = `useFieldArray` + un schéma `z.object({ items: z.array(rowSchema) })` ; selects = `Controller` via `features/candidate/select-field.tsx` (ou `components/ui/select`), `parse` quand la valeur formulaire n'est pas une `string`.
- **Liste d'ids purs** (diplômes, domaines d'étude d'une offre…) = `TagInput` (`components/ui/tag-input.tsx`) : multi-select typeahead en chips (pattern LinkedIn/Greenhouse) branché via `Controller` sur `string[]` — on tape → suggestions du vocabulaire contrôlé (**jamais de texte libre** : seule une suggestion est ajoutable, les FK restent maîtrisées) → Entrée ou clic ajoute la chip, × ou Backspace sur champ vide retire, déduplication automatique ; filtre partagé avec `Select` via `filterOptions` (exporté de `components/ui/select.tsx`). Dès qu'une valeur porte des attributs (niveau, poids, années…), on garde une ligne `useFieldArray` à la place — les chips ne servent qu'aux listes d'ids sans attribut.
- **Champ HTML riche** (description d'offre, D19) = `RichTextEditor` (`components/ui/rich-text-editor.tsx`, Tiptap — Bold/Italic/Underline, H2/H3, listes, Lien http(s) ; `immediatelyRender: false` pour SSR/Turbopack) branché via `Controller` sur un champ `string` (HTML ; `""` = vide). Le HTML **sanitisé au vol** dans la couche API : `sanitizeHtml` (`lib/utils/sanitize-html.ts`, DOMPurify profile `html`) via un helper `htmlOrNull` dans `lib/api/job-offer.api.ts` (vide/`<p></p>` → `null`) — **jamais de HTML cru vers le backend ni stocké** ; le composant n'appelle jamais `sanitizeHtml` lui-même (une seule porte d'entrée). Limite métier dans le schéma (`optionalText(20000)`) et `@Size` backend. Styles du contenu édiité = bloc scopé `.job-offer-description` dans `app/globals.css`. Tests : polyfill `Range.getBoundingClientRect`/`getClientRects` (jsdom, requis par ProseMirror — precedent dans `tests/components/ui/rich-text-editor.test.tsx`).

## API

- Instance Axios unique : `lib/api/axios.ts`, `baseURL = NEXT_PUBLIC_API_URL` (`.env.local`, défaut `http://localhost:9080`). **Exceptions SSE** (D60/D64) : le flux du matching (`streamMatchingStatus`, `lib/api/matching.api.ts`) et les flux de normalisation (`streamNormalizationStatus`, candidat/offre — T-85) passent par `fetch` + `ReadableStream` — axios ne streame pas côté navigateur et `EventSource` n'envoie pas `Authorization` ; même `baseURL` (`api.defaults.baseURL`), même jeton du store, même `clearAuth()` sur 401, jeton **jamais** dans l'URL. L'événement n'est qu'un **signal** : le GET reste la source de vérité, on invalide/relit à réception.
- Messages d'erreur : `lib/utils/api-error.ts` (`getApiErrorMessage`, tests dans `tests/lib/utils/api-error.test.ts`) — ordre `detail` → `title` → réseau → générique. **`detail` est affiché tel quel** : garantie backend (le serveur construit des messages sûrs, jamais un message brut ; voir « Erreurs » de `backend/AGENTS.md`) — aucun filtre n'est appliqué ici.
- Le backend est **Spring Boot** (REST). Un service IA Python/FastAPI est appelé par le backend, jamais directement par le frontend.
- Les modules API par domaine (`auth.api.ts`, `candidate.api.ts`, `admin.api.ts`, …) vivent **uniquement** dans `lib/api/`, et ne sont créés que lorsqu'ils sont utilisés. Aucune fonction API fictive.

## Tests

- **Vitest** + **React Testing Library** + `@testing-library/jest-dom` (environnement `jsdom`). Pas de Jest, pas de Playwright/Cypress pour l'instant.
- Commandes : `npm run test` (watch), `npm run test:run` (CI, non interactif).
- Config : `vitest.config.mts` + `vitest.setup.ts` (matchers jest-dom). Alias `@/` identique au tsconfig.
- **Localisation** : **tous** les tests vivent dans `tests/`, en **miroir de l'arborescence source** (`tests/features/auth/login-form.test.tsx` pour `features/auth/login-form.tsx`), avec `tests/helpers/` pour les cohortes partagées (`test-utils.tsx`). `tests/mocks/` et `tests/fixtures/` : créer uniquement au premier besoin, jamais de dossiers vides pour la forme.
- Ce qu'on teste : logique pure, schemas Zod, stores Zustand avec logique, hooks significatifs, comportements de composants (interaction, rendu conditionnel, formulaires, callbacks). On teste le **comportement**, pas l'existence d'un HTML.
- **Entrées facultatives** (règle racine) : pour chaque recherche/filtre, asservir l'**absent** (1ʳᵉ requête sans clé de filtre), le **vide** (champ effacé ⇒ requête non filtrée) et le **combiné** ; le param-building des clients API (`lib/api/*.api.ts`) a ses tests dédiés — aucune clé envoyée quand le filtre est vide, `page` transmis quand défini, `size` jamais envoyé (le backend décide).
- Interdits : tests bidons « ça existe », faux tests métier sur des fonctionnalités inexistantes, course au 100 % de couverture.
- Une fonctionnalité n'est pas terminée parce qu'elle compile : elle doit venir avec ses tests.

## Conventions

- Langue : **l'UI est en anglais** (`lang="en"` dans `app/layout.tsx`, textes et metadata en anglais). Les échanges de l'équipe sont en français, pas le code de l'application.
- Styles : classes Tailwind uniquement ; pas de fichiers CSS par composant, pas de styles inline sauf nécessité.
- **`cn()` est un simple `join` (pas de tailwind-merge)** : cumuler deux classes conflictuelles (`bg-*` + `bg-*`, `w-full` + `w-44`, `h-11` + `h-12`) donne un ordre de surcharge non déterministe. Résoudre par une **variante** (`Badge` avec `tone`, `Button` avec `variant`) ou un wrapper (`<div className="w-44">` autour d'un bouton `w-full`), jamais en empilant.
- **Attente d'une opération = prop `busy`** sur `Button`/`CtaButton` (mutation, envoi, analyse…) : le bouton montre le `Spinner` partagé (`components/ui/spinner.tsx`, glyphe `progress_activity` — pour un `CtaButton` il **remplace** le glyphe du badge), se désactive et expose `aria-busy`. Un seul geste `busy={…}` — jamais recopier spinner + `disabled` + `aria-busy` (ni `iconClassName="animate-spin"`) ; un bouton qui n'exécute aucune opération (« Review », « Cancel », « Discard ») reste simplement `disabled`, sans spinner. `SectionCard`, `UploadButton`, les formulaires auth, la modale de revue et les actions admin sont déjà branchés.
- **Mouvement réduit** : règle globale `@media (prefers-reduced-motion: reduce)` dans `app/globals.css` (animations/transitions neutralisées système-wide) — les variants `motion-reduce:` locaux ne servent qu'à un effacement ciblé.
- Ne pas développer : permissions fines (RBAC à rôles seulement — le rôle ADMIN et la zone `/admin` existent, mais aucune UI de gestion des rôles ni matrice de permissions), tests e2e, Kafka — hors scope tant que ce n'est pas demandé.
- Vérifier avant de conclure : `npm run lint` puis `npm run build`.
